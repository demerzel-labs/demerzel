## Goal

After M2.5, the full-screen interface is the way to use Demerzel. It
renders model output as formatted text with highlighted code. Thinking
is a block the user can open and close. Each tool call is a card with
its input, status, duration, and output. A progress line shows the
live model call. The input takes several lines and completes
commands. A drag selects transcript text and copies it. Colors come
from a theme. The plain REPL stays as the low-dependency
fallback with its M2 behavior.

## Exit criteria

M2.5 is done when all of these hold:

1. A dogfood session in this repo through the TUI shows every
   element, and a scripted PTY scenario covers each one:
   - formatted model text with highlighted code fences;
   - thinking blocks that open and close;
   - tool cards with status, duration, and an output tail;
   - the progress line while a turn runs;
   - the status bar;
   - a long code fence with a diagram, browsed and copied out.
2. Multi-line input and slash-command completion work in the PTY
   suite. In the PTY suite, a drag selects transcript text and the
   copy goes to the terminal as an OSC 52 write. The Ctrl-C rules
   hold at every point. `--plain` behaves as in M2.
3. Two built-in themes and one config-defined theme render in PTY
   scenarios. `NO_COLOR` and a 256-color terminal degrade without
   error.
4. The render bench on a formatted transcript: one redraw at 120x40
   under 1 ms, and `stream` above 1,000 frames per second. Boot to
   prompt and idle memory stay within 10% of each machine's M2-era
   receipts, on both reference machines
   ([`bench-platforms.md`](bench-platforms.md)). The stripped binary
   stays inside the 15 MB M2.5 budget after the highlighter lands,
   with a `cargo-bloat` receipt. Size is a budget, not a wall: the
   receipt can justify a crossing, function never gets cut for size.
5. `cargo fmt`, `cargo clippy`, `cargo test`, and `cargo doc` are
   clean. The metrics receipt is committed at the close-out.

## Workspace after M2.5

No new crate. `demerzel-tui` gains modules for the block transcript,
markdown, highlighting, cards, the editor, selection, and themes.
`bench/render` gains a formatted-transcript fixture.

```text
crates/demerzel-tui/src/
  transcript.rs   # blocks with a layout cache (rewritten)
  markdown.rs     # markdown events to styled rows (new)
  highlight.rs    # code fence lines to classes (new)
  cards.rs        # tool cards, the progress line (new)
  editor.rs       # multi-line input, completion (replaces input.rs)
  select.rs       # drag selection, the OSC 52 write (new)
  theme.rs        # roles, built-in themes, color depth (new)
  render.rs       # the frame: transcript, progress, input, status
```

## Design

### The block transcript (demerzel-tui)

Today the transcript stores logical lines with a kind, and the
renderer wraps the visible tail. M2.5 stores blocks:

- `Text`: the markdown source of one model reply segment, streamed.
- `Reasoning`: the readable summary, an open flag, a live flag.
- `Tool`: the card — the name, the driver's preview, the state, the
  start time and the duration, the kept output, an expanded flag.
  The transcript maps the call id to the block.
- `Notice`, `Error`, `Prompt`: one line each, as today.

Each block owns a layout cache: its styled rows at the last width. A
width change or a change to the block invalidates the cache. The
renderer walks blocks from the bottom until the viewport is full, so a
long session pays for its window, not its history. Streaming touches
only the open block, so one frame costs that block's re-layout plus
the viewport walk.

Caps carry over: a block count cap of 2,000 replaces the line cap,
and a per-block byte cap of 32 KiB bounds the re-layout of one block.
The worst case is 64 MiB of text plus the row caches. A rendered
reply keeps its rendered rows too, capped at twice its source. A
face table sits next to the rows, one entry of 8 bytes per face
change. Each row adds two entries, under the row cap. A highlighted
fence adds one per class change, capped at a quarter of the row cap
in entries. So one block holds at most 32 KiB of source, 64 KiB of
rows, and 384 KiB of faces. A tool card keeps up to 16 KiB of
output and 8 KiB of preview body next to its text, both sanitized
before the cap, and three lines of 512 bytes: the name, the input,
and the summary. So 2,000 cards hold at most 50 MiB beside their
text. A card that collapses gives the expanded text's memory back
at its next layout. A thinking block that closes gives back its
open form too: the rendered text, the rows, and the faces. A
thinking block keeps its summary beside its text, up to the block
cap less a header reserve. A closed block's text is one line. A
transcript of rendered replies can reach fifteen times the text
bound. In practice the rendered rows are about the size of the
source. The faces of a code source are one to two times its size,
and near zero for prose. The step-10 memory receipt decides whether
blocks outside the viewport must drop their caches.

Follow mode: the view sticks to the bottom until the user scrolls up.
A scroll up enters browse mode and shows an indicator with the count
of rows below the viewport. Rows that arrive or change below the top
of the viewport keep the view in place. `End` returns to follow mode;
at the bottom, `End` stays the cursor key and Ctrl-E is its twin. A
submitted line returns to follow mode, so the reply is visible. A
width change returns to follow mode: the rows the view counted no
longer exist. The mouse wheel scrolls when the mouse is captured.
Mouse capture is on by default since step 8b: the interface owns
selection and copy, and without capture most terminals turn the
wheel into arrow keys on the alternate screen. The `mouse` config
key turns capture off, for a user who wants the terminal's own
selection. A project file can turn capture off. It cannot turn
capture on against a user file that turned it off.

### Markdown rendering

`pulldown-cmark` parses a `Text` block into events. A renderer in this
crate maps the events to styled rows:

- headings, emphasis, and inline code;
- lists with indent and markers, block quotes, and rules;
- links as text with a dim URL;
- tables cut to the viewport width;
- fenced code with a frame and a language label.

The open block re-parses on each frame that changes it. The parse is
linear in the block, and the byte cap bounds it. A fence that is not
closed yet renders as code from its opening line, because the stream
is mid-fence.

Rows wrap at display width with the existing wrap rules. Code rows
wrap too, so every character stays on screen. A block cut at the
byte cap inside a fence hands the fence opener to the next block.
The code stays code, and the frame does not repeat at the seam. A
newline inside a paragraph ends the row. A model writes short lines as lines, the way
chat interfaces show them, so the renderer does not join them. The
rendered rows of one block live in a buffer next to the source. The
cap on that buffer is twice the block byte cap. Prefixes, frames,
and table padding grow the rows, and a block of rules or padded
tables must not grow without bound. A block that reaches the cap
shows as plain text. A `markdown` config key turns the rendering off
and shows the raw text, for copying.

### Syntax highlighting

A built-in scanner in `highlight.rs` classifies the lines of a code
fence: keyword, string, comment, and number. The set: Rust, Python,
JavaScript and TypeScript, Go, shell, JSON, TOML, YAML, and Markdown.
The fence label picks the language. A label outside the set gets the
code face alone. The scanner makes one linear pass over each line.
One state carries to the next line: a block comment, a string that
runs on, or a fence inside a markdown sample. The tables are static,
so nothing loads at boot or on the first fence. A class lands on the
row as a face bit over the code face, and the theme maps the four
classes to colors.

A block cut at the byte cap inside a fence continues with a fresh
state. A comment or a string that is open across the cut reads as
code until its closer. The closer then opens a comment or a string
that runs to the next closer. The result is wrong classes on a
stretch, never a lost row.

Step 4 measured `syntect` before it decided, on the Linux reference
machine, release profile. The features: the default syntax set,
`regex-fancy`, and `dump-load`. The pure-Rust regex engine was the
candidate. The other engine is a C library: it needs a C toolchain at
build time and adds a second regex engine to the binary.

- Binary: +648 KB stripped, 8,305,200 to 8,953,056 bytes, inside the
  15 MB budget.
- Load: 0.7 ms for the syntax set, then about 20 ms of regex
  compilation on the first fence of each language.
- Parse: the Rust grammar ran at 0.4 MB/s, 75 ms for one 32 KiB
  block; Python ran at 90 MB/s after its first fence.
- The default set has no TypeScript grammar and no TOML grammar.

A block renders whole on every changed frame. A Rust fence at the
block cap would then hold one frame for 75 ms and stall input while
it streams. A per-line state cache would fix that at the cost of a
second cache next to the layout cache. The built-in scanner renders
the same 32 KiB block in about 400 µs on the same machine and
profile. The scan is 280 µs of that. The fixture is one language per
fence at 120 columns. The theme maps four classes either way. The
decision: the built-in scanner. It adds no dependency. It adds 21 KB
to the binary.

### Tool cards and the progress line

One card per tool call, one block in the transcript:

- Header: the state glyph, the tool name, and the input line. The
  input line is the first line of the driver's preview, without the
  tool name when the line repeats it: `· bash $ cargo test`,
  `· edit src/main.rs`.
- Body: the rest of the preview — the diff for an edit, the command
  lines for bash — capped as in M2. A call with no dispatch preview
  shows the question's own preview here.
- Footer: the last five output lines, then one line with the
  duration and the tool's summary. The card cuts a long tail line at
  240 bytes. Ctrl-O expands every card to its kept output and
  collapses them again. New cards follow the toggle.

The states and their glyphs: running `·`, pending approval `?`, done
`✓`, error `✗`, declined `⊘`, interrupted `✗`. The approval question
stays on the input row; the card shows `?`. A declined card keeps the
refusal as its result; its footer says `declined`. The interface
measures the duration between `ToolRun` and `ToolEnd`. A call that
asked counts from the answer, so the time at the question stays out.

Engine-event growth: `ToolEnd` carries the tool's output text,
borrowed. The interface sanitizes it and keeps the last 16 KiB. The
footer names the cut, and the expanded view marks it. The card holds
the kept output next to its rendered text. A card renders at its
next layout, not at each change. The expand toggle marks every card
and renders the cards the frame walks. In follow mode, that is one
viewport. In browse mode, the walk covers every card below the
viewport to hold the anchor. A probe measured that walk: 3 ms at 400
rows of 16 KiB cards, 94 ms at the block cap browsed to the top. A
block anchor would remove the walk; step 10 decides with the
receipt. A card that grows or shrinks in place reports its row
change through the frame walk, so the anchor holds.

The driver renders each dispatching call's preview and sends it with
`EventSender::tool_preview`, keyed by the call id. The interface
crate still knows nothing about tools.

The progress line is one row above the input while a turn runs. It
shows a spinner, the elapsed time since the turn started, and the
stage: `thinking`, `writing`, or the running tool's name. A tick
timer wakes the loop ten times a second during a turn. Nothing wakes
at idle. The prompt is `❯`. On a screen of eight rows and sixteen
columns or more the input box has a frame: a dim box with rounded
corners and a blank row under the input. The status sits on the
frame's bottom edge: the model, the mode, the effort, and the
totals, each between line segments. The segments take the `dim`
role, so the typed text reads apart. A `/model` or `/effort` switch
moves the status. A framed screen has no bar row. The progress line
then gets a blank row above it, apart from the reply. A smaller
screen keeps every row and column for content. It shows the status
as a bar under the input, and the `status_bar` role paints only
that bar. A press on the browse indicator is the End key.

### Thinking blocks

One `Reasoning` block per reasoning segment, in `thinking.rs`. The
engine emits `ReasoningEnd` when a segment ends, so a block has a
boundary. Before step 6 only `ReasoningDelta` reached the sink. A
thinking block shows one reasoning summary from the model. The
block is the container, whatever its state. Its state reads
`thinking` while live and `thought` when finished; the provider
streams `reasoning`. A line is text up to a newline; a row is what
the width shows of it. A closed block is one line: the state, then
the summary's first line. While deltas arrive the state reads
`· thinking`. After the end it reads `▸ thought for 2.0s`. A mark
follows the line when more text exists. The line wraps at the width
like any other. An open block shows the state on its own row, a
blank row, and the whole summary. Ctrl-T opens the newest block and
closes it again. The `thinking` config key sets how a block starts:
`closed`, the default; `open`; or `hidden`, which drops the text.

The summary renders as markdown when the transcript does, so the
marks a model writes show as faces, not as asterisks. The blank row
under the header keeps the header a paragraph of its own. Without
it, a summary that starts with `---` turns the header into a
heading. The block keeps its summary up to the block cap less a
header reserve; a longer summary is cut with a mark. A segment whose
turn ends first reads `thinking interrupted`. Whitespace alone opens
no block: the Codex adapter sends a paragraph break between summary
parts. The deltas of one segment extend its block, whatever lands
behind it; the transcript keeps the live block's index, as it keeps
the running card's.

The block's clock starts at the last event that is not reasoning
text, not at the first delta. The events that set it:

- the turn's start;
- any display event but reasoning text, at the time it lands;
- a tool's end and a segment's end, at the time the event carries.

A provider can stream the summary after the reasoning; the Codex
endpoint does, so its first delta comes at the end of the thought.
A provider that streams the summary live loses nothing: its first
delta follows that point at once.

The live row carries no spinner and no elapsed time. The progress
line shows both, and a block that rendered again every tick would
cost its summary ten times a second. The render bench fixture has
no reasoning path. A probe on the release build put a closed live
block at 0.001 to 0.007 ms per frame over the floor. An open block
of prose is level with the text path under markdown. An open block
past the render cap keeps its plain verdict while it grows, as a
reply does. Step 10 decides whether the fixture gains one.

### The input editor

The editor holds several lines, in `editor.rs`. Alt-Enter inserts a
newline; Enter submits. Shift-Enter inserts a newline too when the
terminal supports the keyboard-enhancement flags. Pasted newlines
stay. The input box grows to eight rows. It scrolls inside them.
The transcript keeps one row at least. Rows wrap hard at the width
of the input box, so every character stays on screen. One column
stays free at the right. The cursor sits there after a full row.
The prompt occupies the first columns of the first row, and every
other row indents by as much. The rows are a layout cache on the
editor. An edit or a width change rebuilds them. The rebuild is
linear in the buffer, and it runs once per edit. On the Linux
reference machine, a 64 KiB paste of prose costs 130 µs. A 1 MiB
paste costs 2 ms. The cost is per row: a paste of newlines alone
costs four times as much. The cache holds 16 bytes per row, and it
keeps up to twice its row count as room to grow. A frame walks only
the rows it shows. Up and Down move across rows. On the first row,
Up shows the previous history entry. On the last row, Down shows
the next entry. The editor then shows every line of the entry.
Home, End, and the M2 kill keys act on the cursor's line. Ctrl-K at
a line end joins the next line. Ctrl-W at a line start joins the
previous one.

The interface pushes one keyboard-enhancement flag on the alternate
screen. The flag tells modified keys apart. The interface pops the
flag before it leaves the screen. It sends the push without a query.
A terminal without the protocol ignores the sequence. A query costs
a round trip at boot. A silent terminal makes the query wait two
seconds. The PTY suite is such a terminal.

Typing `/` opens the completion popup with the command registry:
usage and help per command, for the commands whose name starts with
the line. The popup sits over the rows above the box, at the
prompt's text column. Tab and the arrow keys select. Enter puts the
command on the line, with a space after a command that takes
arguments. The next Enter submits the line. Esc closes the popup
until the next edit. The registry stays in the binary crate. The
interface receives the list through its options, so M3 custom
commands extend the same list. The list only completes the line.
The driver dispatches the submitted line, and the driver alone
defines a command name.

### Theming

A theme maps named roles to colors. The roles:

- text, dim, accent, error, success, warning;
- heading, link, inline code, code block;
- prompt, the status bar, the progress line;
- diff add and diff remove;
- the highlight classes.

Each face keeps its attribute — bold, dim, italic, underline — and
the theme adds the color of the face's role. Under `NO_COLOR` the
attributes alone carry headings, emphasis, links, marks, and
thinking; inline code and an error block read by their text. The
accent paints the card header, the selected completion, and the
browse indicator. The state mark on a card takes success, warning,
or error. A `+` or `-` line of an edit preview takes the diff roles.

Three themes ship: `terminal`, the default, which names the
terminal's own palette entries and no RGB value; `dark`; and
`light`. Config picks one and can define more:

```toml
[tui]
theme = "dark"
markdown = true
thinking = "closed"
mouse = true

[theme.ocean]
accent = "#5fafd7"
error = "#ff5f5f"
```

A `[theme.<name>]` table in the user file edits a built-in theme, or
starts a new one from `terminal`. A project file picks a theme by
name; its tables are ignored with a warning, because a color can
hide the approval question or a preview. A value is `#rrggbb`, a
palette name, or `none`. [`config.md`](config.md) lists the roles
and the forms.

The interface fits the theme once at boot. Truecolor applies when
`COLORTERM` or a direct-color `TERM` declares it; a 256-color
terminal gets the nearest palette entry; any other terminal gets
the nearest of its sixteen; `NO_COLOR` sets no colors. A project
file can set the `[tui]` keys: they are cosmetic and cannot raise
privilege. Two exceptions: a project file cannot turn `mouse` on
against a user file that turned it off, and it cannot define a
`[theme.<name>]` table.

### Selection and copy

A drag over the transcript selects text. The transcript owns the
points and the row map; `select.rs` holds the geometry, the copy,
and the clipboard write. The mouse mode gains button-motion
reporting: mode 1002 replaces mode 1000 in
the capture sequence, and the release sequence covers it already.
The terminal reports the pointer while a button is down. The
terminal reports nothing at idle. The selection is two points in
transcript rows and columns: the press and the pointer. A point
names a block by its absolute index, a row of the block's layout,
and a column, so it holds still while content arrives below it.
The frame records the block and row on each viewport row, and a
mouse position maps through that record. The frame renders the span
reversed over the rows it shows, in the highlight style of the
browse indicator. The rows keep their layout; the frame adds a
column split and up to two spans per selected row. A release with a
span copies the text and leaves the highlight on the screen. The
copy holds the shown rows between the points. The copy leaves out
the marks the frame adds: every span the renderer marks as
structure, a card's header row, indent, and hint, and the prompt on
an echo. A code fence gives its code without the frame. A card
gives its output and its result line without the header. A row of
whole-row structure — a fence frame line, a rule — adds no line. A
row of marks that can hold text, such as a quote's bar, adds a
blank line; a wrapped row of marks alone, such as a card's hint on a
row of its own, adds nothing. A newline joins each row. The copy
cuts trailing spaces. The copy is cut at 64 KiB, in bytes or in
rows. A notice names the cut. The write blocks the loop,
and terminals cap the sequence near that size. The copy goes to the
terminal as an OSC 52 write, so it works over SSH and inside a
multiplexer that forwards the sequence. The base64 encoder is twenty
lines in `select.rs`. The encoder adds no dependency. A click
without a drag clears the selection. A change to a block under the
selection clears it: a delta, a card update, a thought that ends or
toggles, the expand key. A width change clears it, and so does the
first block dropping off the cap. Content that arrives below the
selection leaves it. A press or a drag names no row of a block that
changed since the last frame: the screen still shows the old rows.
A drag onto a blank cell of the pane runs to the last row's end; a
drag below the pane, onto the completion popup, or onto the browse
indicator leaves the head where it is. The wheel keeps scrolling
during a drag. Two items wait for dogfood: word selection on a
double click, and a copy key that needs no mouse.

### The project and the branch on the status

The status names where the session works: the project directory's
name and the git branch, as two segments between the effort and the
totals: `╰─ model ─ mode ─ effort ─ project ─ branch ─ totals ─╯`.
The bar on a small screen shows the same. The project is the
session's directory, so the name is its last path component. The
branch comes from `.git/HEAD`. The driver walks up from the project
directory to the first `.git`, reads the file, and shows the branch
name after `ref: refs/heads/`. A detached head shows the first seven
characters of the hash. A worktree's `.git` file names its git
directory, and the read follows it. No `.git` shows no branch
segment. The read adds no dependency and runs no process. The driver
reads once at boot and again at each turn's start. A checkout
between turns shows at the next prompt; nothing polls. A branch name
is untrusted text: the interface cuts it at 64 bytes and sanitizes
it like a tool name. A wide status cuts from the right, so the
totals go before the branch. A segment shows whole or not at all, so
a cut count never reads as a number. The model alone cuts with a
mark, so a narrow status still names it. The read takes one line and
4 KiB at most. The read opens a regular file only, so a stray `.git`
entry cannot block the interface. Out of scope: the dirty state, the
ahead and behind counts, the remote. Before the two segments land,
the step folds the status setters of `EventSender` — `model`,
`effort`, and the two to come — into one call that takes a status
patch, so the public surface stops growing with the segment count.

### The approval mode at runtime

`/approval` shows the mode; `/approval read-only|ask|auto` sets it
for the turns that follow, in both interfaces. Shift-Tab in the
full-screen interface cycles it — `ask`, `auto`, `read-only`, and
back — while the completion popup is closed; the popup owns
Shift-Tab while it is open. The switch is the user's at the
keyboard, so the project-file floor does not apply: the user can
set any mode. The engine gains `set_approval`, next to `set_model`
and `set_effort`. It swaps the approver and the tool set at the
next turn's start: `read-only` drops the write and execute tools,
`auto` asks nothing, `ask` asks again. The session grants from
`always` answers survive a switch; `read-only` ignores them because
the tools are gone. A pending question stays open through a switch;
the mode applies to the calls after it. The switch lands on the
session file as a `meta` record, as a model or effort switch does;
the record gains an `approval` field, optional, so old files still
read. The status names the mode in force. A one-shot run has no
command and no key, so its mode is the one the flags and the config
set.

### The context on the status

The status names the context in use: the input tokens of the last
model call, which is the prompt the model just read. The segment
reads `context 34.2k`, labeled like the effort. It sits between the
branch and the totals:
`╰─ model ─ mode ─ effort ─ project ─ branch ─ context ─ totals ─╯`.
The totals stay. They count the session's spend across calls, and
the context counts one prompt, so the two must not read as one
number. The usage event carries the count already. The interface
keeps the last call's value, and a fresh session clears it. When
the model's context window is known, the segment adds the share:
`context 34.2k · 17%`. The window comes from two places. Each
provider's adapter gains a model catalog with a `context_window`
column, a static table. A `context_window` key under
`[providers.<id>]` names the window for a model the table does not
name. A model with no window shows the count alone. The same table
feeds the M4 compaction trigger, so the number lands once. Cache
reads count as context: the model read them.

### Quit on Ctrl-C and the resume hint

Ctrl-C on an empty input box asks once: the status shows `press
Ctrl-C again to quit` for three seconds, and a second press inside
that span ends the session. A press on a box with text clears the
box first, as today. The rules during a turn and at a question do
not change: Ctrl-C stops the turn. Ctrl-D and `/exit` still end
the session at once. The REPL keeps the same two-press rule on its
prompt, with the hint on stderr.

Every exit path prints one line on stderr after the screen restores:
`session <id> · resume with demerzel -c`. A run that opened no
session prints nothing. The CLI gains `--session <id>`, which
resumes that session in the project instead of the latest; an id
with no file stops the run with a clear error. `-c` keeps its
meaning. The hint names `-c`, the short form, because the latest
session is the common case.

### The first-run screen

When no provider credential resolves, the interface shows one screen
before the prompt. It holds the logo, the credential state per
provider from the doctor probe, and the login commands. Enter
continues to the session, where a turn fails with the clear
credential error until a login lands. The cross-harness credential import — the jcode
first-run design target in the project notes — waits for M3
discovery.

### Measurement

The render bench gains a formatted-transcript fixture: markdown with
headings, lists, tables, and code fences, plus cards and a thinking
block. `frame`, `ingest`, and `stream` run on it, and a `reflow`
bench measures a width change. Exit criterion 4 names the gates. PTY
scenarios cover each element; a resize forces the full repaint the
frame diff otherwise skips, the step-6 lesson.

## Dependencies

Each new dependency passes a `cargo-bloat` check against the 15 MB
M2.5 budget and the 25 MB budget
([`bench-platforms.md`](bench-platforms.md)). Dev-only crates are
exempt.

| Crate | Purpose |
|---|---|
| pulldown-cmark (no default features) | markdown parsing |

Not added: `syntect`, which step 4 measured and declined (see Syntax
highlighting); a ratatui markdown widget crate; an image protocol
crate; a custom terminal renderer. The markdown renderer lives here
so streaming and the theme stay in one place.

## Decisions to make during M2.5

- The REPL — decided now. Presentation work is TUI-only. The REPL
  keeps its M2 behavior, the shared engine events, and the shared
  command registry. Parity tests cover the events and the commands,
  not the look.
- The highlighter — step 4. Step 4 measured `syntect` and chose the
  built-in scanner; the receipt is under Syntax highlighting.
- Mouse capture default — step 2, reversed after the step-7
  dogfood, reversed again in step 8b. Step 7 turned it off: capture
  took the terminal's own text selection, the Shift-drag override
  depends on the terminal, and in the dogfood Shift-drag selected
  nothing. Step 8b turns it on: the interface owns selection and
  copy, and the step-7 dogfood's strongest finding was that without
  capture, terminals turn the wheel into arrow keys on the alternate
  screen, which browse the history instead of the transcript. The
  `mouse` key turns capture off. A project file cannot turn it on
  against a user file that turned it off.
- The clipboard path — step 8b. OSC 52: one write, no clipboard
  tool, works over SSH and inside a multiplexer that forwards it. A
  terminal that refuses the write loses the copy in silence; the
  interface cannot tell. Dogfood decides whether a notice or a
  fallback tool is worth the surface.
- The input box's frame — step 8b, after dogfood. Daniel found the
  box and the status bar packed too tight, with nothing to mark the
  box, and the `dmz>` prompt heavy. The prompt is `❯`, in both
  interfaces: one constant, one bench marker. A box with rounded
  corners around the input, the prompt flush with its edge, and the
  status on its bottom edge between line segments, on screens of
  eight rows and sixteen columns or more; three rows and two columns
  of chrome, and no bar row. A small screen keeps the bar, and the
  `status_bar` role paints only that bar: on a framed screen the
  role is idle, by this decision, not by neglect. The render bench
  runs framed, so its `frame` numbers lay out 36 transcript rows
  where the step-8 receipt laid out 38; step 10 states that next to
  the receipts.
- A press on the browse indicator — step 8b, after dogfood. The
  indicator names the End key, and with capture on it reads as a
  button; a press on it returns to follow mode. Other clicks stay
  out of scope.
- The project and the branch on the status — step 8c, added in
  step 8b's dogfood. Daniel asked where git and the working
  directory show; nothing in the plan did. A read of `.git/HEAD`
  per turn, no git process, no dependency. Dirty state and
  ahead/behind counts stay out: each needs a git process or an
  index parse, and the value is not proven yet.
- The approval mode at runtime — step 8d, added in step 8b's
  dogfood. Daniel asked for a knob between asking and running
  free. The config key and the flags set the mode once per run;
  `/approval` and Shift-Tab set it mid-session. The switch is the
  user's, so no trust floor applies to it; a project file still
  cannot raise the mode a run starts in.
- The context on the status — step 8e, added in step 8b's dogfood.
  Daniel asked how hard a context readout is. The count is one
  field of the usage event; the share needs the window, which
  nothing knows today. The window goes in the model catalog with a
  config override, because the M4 compaction trigger needs the same
  number. Auto-compaction stays in M4.
- The turn time on the usage line — step 8b, after dogfood. The
  usage notice after a turn reads `· 836 in · 688 out · 0 cached ·
  4.2s`: the time since the turn started, in both interfaces. On a
  turn with several model calls, each call's line shows the time so
  far, and the last shows the turn's length.
- The effort on the status — step 8b, after dogfood. The status
  names the reasoning effort as `effort high`, labeled so it reads
  apart from the mode, and `/effort` moves it. The status must show
  the configuration in force.
- Quit on Ctrl-C — step 8f, added in step 8b's dogfood. Daniel
  found Ctrl-D the only way out and no resume hint on the way out.
  Two presses, not one: a stray Ctrl-C must not end a session, the
  M1 rule. The hint on the status, not in the transcript: it is
  not content. `--session <id>` joins `-c` because the exit line
  names an id and nothing took one.
- The session id off the status — step 8b, after dogfood. The
  26-character id was the longest thing on the status and the least
  useful. `/session` shows the open session's id and file in both
  interfaces; the status keeps the model, the mode, and the totals.
- The popup on a history recall — step 8b. A recalled entry that
  starts with `/` opens no popup; the arrows keep browsing the
  history, and the next edit opens the popup again. Before this, a
  recalled command opened the popup, and the arrows moved its
  selection instead of the history.
- The `End` key — step 2, kept in step 7. It returns a browsed
  transcript to follow mode; at the bottom it is the cursor key.
  The rule holds with several lines in the editor. End moves to the
  line end. Ctrl-E does the same while the user browses the
  transcript.
- The browse anchor — step 2, kept in step 5 and step 7. A row count
  from the end, adjusted for rows that change below the viewport
  top. A card that grows or shrinks in place reports its row change
  through the frame walk, so step 5 needed no anchor on a block. A
  viewport height change adjusts the count by the rows lost or
  gained, so the top row holds when the input box grows.
- Code rows: wrap or cut — step 3. Wrap: every character stays on
  screen, and a cut code row hides the part that matters.
- A newline inside a paragraph — step 3. It ends the row. The
  parser calls it a soft break, and a web page joins the lines. A
  chat interface shows a line break, and models write for that.
- Thinking default state — step 6. Closed: one line per segment. A
  long summary is the model's working, and the reply follows it.
- The thinking key — step 6. Ctrl-T toggles the newest block only.
  Ctrl-O toggles every card, because a card's output is evidence
  the user compares across calls; a thought is read once. Older
  blocks stay reachable: the toggle acts on the newest, and the
  `open` setting shows every block from the start. The closed line
  names no key, unlike a card's footer: the line is the summary's
  own, and a hint on every one is noise. The key is documented in
  [`config.md`](config.md).
- The reasoning-end event — step 6. A struct variant with no
  fields, marked `#[non_exhaustive]`, so a later field — a redacted
  segment — stays additive. The sink already saw the deltas, and
  the interface measures the duration itself. A segment with no
  summary, a redacted one, ends without a block.
- The thinking clock — step 6. One owner, on the app: the time of
  the last event other than reasoning text. A segment-start event
  from the provider would be exact; the adapters drop the
  item-added events today. Take it when a provider's summary timing
  needs it.
- Shift-Enter through the keyboard-enhancement flags — step 7. The
  interface pushes the disambiguate flag without a query, and a
  terminal without the protocol ignores it. Alt-Enter is the
  portable path. The PTY suite drives both key forms and pins the
  push.
- Reverse history search (Ctrl-R) — step 7, after dogfood: not in
  M2.5. Up and Down reach a session's entries in a few presses, and
  the editor now shows every line of an entry. A search over the
  500-entry file needs an input row of its own. It lands with the
  M3 command work. The popup's row layout can then show the
  matches. The REPL's line editor has the key today.
- Aliases in the popup — step 7. The popup lists each command in
  the registry. It lists no alias. `/quit` dispatches as the M1
  alias of `/exit`; the help line of `/exit` names it. M3 custom
  commands follow the same rule.
- The editor buffer — step 7. No cap. The transcript cuts a prompt
  block at 32 KiB. The history skips an entry over 8 KiB. The
  editor keeps what the user pastes. The cost is the re-layout
  above, once per edit. The render bench measures an empty editor.
  Step 10 decides whether the fixture gains a filled one. The step-7
  receipt reads `ingest` 11% over main in an A/B on the same box,
  with no source change on that path; step 10 measures it with
  instruction counts before it reads the number as a cost.
- `ToolEnd` output — step 5. The full text borrowed; the interface
  keeps a 16 KiB tail, cut before the channel. The render bench does
  not move: the frame path gains one row and the faces of the cards
  on screen. The bench fixture holds no cards yet. An out-of-tree
  probe put card rows and plain rows inside noise of each other.
  Step 10 adds cards to the fixture.
- The expand key — step 5. Ctrl-O toggles every card at once. No
  card selection exists before mouse clicks, which are out of scope.
- The theme config shape — step 8. `[tui] theme` plus
  `[theme.<name>]` tables, as above. A table with a built-in name
  edits that theme; a new name starts from `terminal`. No `base`
  key: the name is the base.
- Project themes — step 8, after an external review. A project
  file picks a theme; only the user file paints one. A repository
  that sets `warning`, `text`, and `status_bar` to one color hides
  the approval question and the mode, the thing the preview rules
  protect. The trust rule already said a project file cannot raise
  privilege; this is the same rule for colors. `none` on a role
  resets to the terminal's foreground even inside a colored span,
  so the word means one thing.
- The `terminal` theme — step 8. It names palette entries, not
  "no colors": the fence's cyan and the error's red from steps 3
  and 4 stay, so the default looks as it did. The backend writes a
  palette entry as `38;5;n`; a sixteen-color terminal took that
  before step 8 too.
- The card frame role — step 8. Dropped. Step 5 built cards with a
  header and an indent, no frame glyphs. The header takes the
  accent; the code fence's frame is a markdown mark and takes dim.
- The depth read — step 8. The interface reads `NO_COLOR`,
  `COLORTERM`, and `TERM` itself, once at boot; the binary passes
  the theme. The interface writes the colors, so it owns the fit.
  A bad theme name stops the run, like any bad value on a known
  key; `doctor` counts it as a problem.
- Diff lines on a card — step 8. A content rule: a preview line
  that starts with `+ ` or `- ` takes a diff role. The interface
  knows no tool names, and the edit preview is the one that writes
  such lines.
- The built-in palettes — step 8. Demerzel's own values, not a
  published scheme's; the review found six values that matched one
  and they moved. The render bench measures the `terminal` theme:
  a colored theme adds bytes on the wire, not work in the buffer,
  and the headless backend writes no wire.

## Risks

- **Binary size from the highlighter.** Closed in step 4. The
  built-in scanner adds no dependency. It adds 21 KB to the binary.
- **Frame cost from re-parsing markdown.** Mitigation: the layout
  cache; only the open block re-lays out; the byte cap bounds it; the
  render bench gate.
- **Reflow on resize.** Mitigation: the cache is keyed by width and
  only the visible blocks re-lay out.
- **Terminal compatibility.** Keyboard enhancement, mouse capture, and
  color depth differ across terminals. Mitigation: a named fallback
  per item; the PTY suite runs with and without each feature.
- **Two interfaces drift.** Accepted by design: the REPL is the
  fallback. The shared events and the registry keep the behavior one.
- **Scope creep.** The exit criteria are the fence. Panes, images, and
  a palette stay out.
